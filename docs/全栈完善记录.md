# FreeMusicPlayer 全栈完善记录（2026-10-25）

本轮围绕全栈面试中可演示、可解释、可验证的业务完成改进：多源搜索可靠性、持久化导入任务、私有歌单、账号统计、权限隔离、运行诊断与自动化验证。继续使用已有 Vue / Spring Boot / MySQL / Redis / 音源侧车，没有重写音频引擎或替换真实曲库。

## 1. 可以直接体验的功能

| 入口 | 新行为 |
| --- | --- |
| 曲库搜索 | 各平台独立请求，先返回的平台先展示；显示搜索中、已返回、无结果、暂不可用 |
| 音乐工作区 → 导入任务 | 提交公开歌单链接，查看任务状态、逐条结果、进度；支持取消与重试 |
| 音乐工作区 → 个人歌单 | 查看成功导入的目录，原播放器播放与收藏；重命名、确认删除；每页20条 |
| 音乐工作区 → 听歌统计 | 近30天累计时间、有效播放次数、不同歌曲数、常听排行与账号最近播放 |
| 管理端 → 运行与任务诊断 | 音源搜索计数/耗时、缓存命中、请求合并、冷却；任务执行器、最近任务、HTTP指标与工作区审计 |

工作区中的私人歌单与原管理端公共歌单分开，不改变已有公共歌单路由。只导入曲目元数据与平台ID，播放时动态解析；目录可导入不等于每个条目都可完整播放。

## 2. 搜索、播放与封面

- `src/api/system.ts` 增加渐进式搜索，保留每个平台的实际结果；搜索中途切换关键词会中断上一轮，避免旧结果覆盖新查询。
- 搜索页保留现有本地查询、平台/歌手条件、试听筛选和分页。新查询会清理上一轮本地分页快照，避免旧歌曲短暂混入。
- Node 引擎调用限制6并发、60等待，排队5秒超时；相同进行中查询合并。正结果缓存30秒、正常空结果4秒、缓存最多200个键；全部失败不会当成正常空结果缓存。
- 单引擎连续3次异常后冷却30秒。删除“全部失败后再重复请求一遍相同 Meting 音源”的逻辑。
- 播放/缓冲20秒无有效推进时进入原有有限换源和失败处理。底层播放状态、切歌、音量和队列事件继续由真实 `HTMLAudioElement` 驱动。
- 换源前结算原播放会话。试听、未知、时长匹配和完整播完仍分别记录；没有新增VIP解密或凭空保证免费完整播放。
- Go封面代理拒绝本机/私网地址、校验DNS结果并固定连接地址、逐跳校验重定向、限制图片类型与5MB体积，设置DNS和读取超时。封面失败沿用统一占位图。
- 源调用的Meting底层网络请求不能被强制取消；限制的是逻辑并发，不声称完成了连接级资源隔离。

## 3. 持久化导入任务

支持网易云 `https://music.163.com/playlist?id=…`（含常见 `#/playlist`）、QQ `https://y.qq.com/n/ryqq/playlist/…`、B站 `https://www.bilibili.com/video/BV…`。

`ImportTarget` 只解析白名单站点的HTTPS链接和平台ID，拒绝任意URL、私网、凭据、端口和短链接；后端访问的是配置好的音源服务，不直接请求用户提交的URL。

流程：创建任务 → QUEUED → RUNNING → 获取真实目录 → 原子落盘目录 → 逐条事务处理 → SUCCEEDED / PARTIAL / FAILED。取消后进入 CANCELLED，运行中取消要等待当前上游调用或事务边界。

- 幂等键由前端生成，唯一约束为 `(user_id, request_key)`；相同键重复提交返回同任务，换链接复用该键返回409。
- 相同用户同平台歌单归入同一个个人歌单，条目按平台ID去重。每个用户最多5个活动任务，每次目录1–1000条；不是无限抓取器。
- 执行器2线程、等待队列4；数据库条件更新认领任务，不依赖内存队列保存任务本身。
- 目录一次性事务写入，避免进程在目录写到一半时留下不完整的已加载目录；每个成功条目单独事务检查点。
- 正常关闭释放自己认领的任务；意外退出后，超过2分钟未更新的RUNNING任务重新排队或完成取消。定时调度间隔约1.5秒。
- 重试保留成功条目，只重新处理失败/待处理项；已经取得的目录不会每次重新抓取。要取得源站后来新增的条目，可用新幂等键创建一次新导入。
- 用户可查看具体失败条目。成功指元数据已进入私有歌单，不表示已探测音频权限或完整可播。
- 读取私人歌单时根据稳定平台标识重建当前部署的媒体入口，避免旧后端端口永久写死。

数据库：`fmp_collection`、`fmp_collection_song`、`fmp_import_job`、`fmp_import_item`；唯一索引、所有者/时间索引、条目外键及删除级联见 `src/main/resources/db/20261025-workspace.sql`。

## 4. 账号统计与数据安全

前端只累计正常时间推进且实际播放中的秒数，跳转进度不增加已收听时间。登录后播放累计3秒开始上报，随后约15秒和暂停/切歌/页面退出时发送累计值。

服务端 `fmp_play_session` 以 `(user_id, session_id)` 唯一；固定会话歌曲身份，事务锁定该行后只接收累计值增量。重复和乱序请求不重复增加时间，单次接收上限60秒，并受服务端经过时间+5秒容差约束。

统计以上海时区聚合近30天，至少3秒的会话计有效播放。每日汇总、排行与最近播放从真实数据库读取。统计依然属于客户端上报数据，不能作为反作弊结算、版权验证或完整音源证明；离线与退出时最后一段可能丢失，跨午夜的长会话归开始日期。

所有 `/workspace/**` 操作从已验证JWT提取用户ID，不接受前端自报owner。任务、歌单、统计查询带所有者条件；越权记录统一404。普通用户无法访问 `/admin/ops/**`。删除歌单需要确认，活动导入期间不能删除目标歌单。

注销账号会在原有注销事务中清理新任务、私人歌单及统计，工作区审计中的用户ID匿名化；前端切换账号时清空工作区状态并取消旧查询。

另外修复旧收藏服务的跨账号缓存风险：收藏歌曲与收藏歌单的缓存键加入已验证用户ID，旧共享键不再读取。导入歌单读取时从当前账号真实收藏表合并收藏状态，不把JSON中旧的喜欢状态当成当前状态，保留已有收藏/取消收藏操作。

## 5. 日志、指标与审计

- Java 请求过滤器生成或验证 `X-Request-Id`，响应暴露给浏览器，日志记录路径、状态和耗时；搜索/导入请求向Node传递相同编号。Node记录不含查询串的请求日志。
- 新工作区操作落入 `fmp_audit`，记录用户、动作、资源ID和请求编号。不是所有旧管理操作都已经接入这张审计表。
- 参数校验日志仅记录字段名，避免校验异常把输入密码打印出来。未知异常对外返回通用错误和请求编号，前端显示编号便于定位。
- Micrometer提供按路由/方法/状态码的请求次数、平均和窗口最大耗时；后台展示实际任务与执行器状态。
- `/admin/ops/prometheus` 在管理员鉴权后输出真实Prometheus文本。没有伪造吞吐量、p95、可用率或“性能提升百分比”。

## 6. 新接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST / GET | `/workspace/imports` | 创建 / 列出自己的任务 |
| GET | `/workspace/imports/{id}`、`/{id}/items` | 自己的任务与条目明细 |
| POST | `/workspace/imports/{id}/cancel`、`/{id}/retry` | 取消 / 重试 |
| GET | `/workspace/collections`、`/collections/{id}/songs` | 自己的歌单和歌曲 |
| PATCH / DELETE | `/workspace/collections/{id}` | 重命名 / 删除 |
| POST / GET | `/workspace/listening` | 累计播放上报 / 自己的统计 |
| GET | `/admin/ops`、`/admin/ops/sources`、`/admin/ops/prometheus` | 管理员运行诊断、音源诊断与指标 |

这些都是本轮实现的真实接口，用户页没有静态假歌单或假统计。浏览器测试使用的接口桩仅存在 `tests/e2e`。

本轮本机验证：后端20项（公共模块5，服务模块15，包含5项隔离MySQL集成测试）、Provider 11项、前端工具12项，共43项通过。

MySQL通过Testcontainers临时容器运行，测试任务幂等与隔离、部分成功保留、取消、重复统计、旧租约恢复、注销清理，以及无演示账号的生产空库初始化、BCrypt管理员只创建一次、重复迁移。没有向使用中的数据库运行清空测试。

Playwright在桌面Edge验证了构建产物和开发页面：慢音源未结束时先显示快音源、真实WAV音频播放、进度拖动、播放上报和工作区分类；检查窄窗口无横向溢出，未捕获的控制台错误为0。WAV与接口桩只用于测试，不参与产品曲库。

管理端也用短时本地测试会话实际打开“运行与任务诊断”，确认音源、任务和审计区域可显示，未捕获控制台错误为0；测试会话已撤销。开发服务器未识别新路由的问题通过重启本项目管理端解决。

另用真实开发后端、Mailpit和两个临时注册账号验证：重复导入返回同任务、越权404、统计互相隔离、重复上报不重复计时、普通用户访问运维403；真实B站目录导入成功24条，管理员诊断与Prometheus返回有效结果。账号和测试数据已注销清理。这不是第三方音源长期可用率测试。

## 9. 用于面试的讲述范围

可以围绕三个可演示问题展开：

1. 上游平台快慢不一或失败时，如何用渐进展示、请求合并、短缓存、并发上限和冷却改善体验。
2. 歌单导入如何在重复提交、部分失败和进程退出后保持可解释状态：幂等键、数据库状态机、事务检查点、执行租约和所有者校验。
3. 真实播放如何产生账号统计，如何处理快进、重发、乱序、退出和隐私清理，以及为什么客户端上报不能作为权益/完整播放证明。

简历可写“基于既有开源播放器二次开发，完成上述模块”，明确自己负责的部分和上游来源。现在已有可运行业务与测试证据；不要写没有测过的高并发数字，也不要把第三方解析器包装成自己实现的解密算法。

尚待后续专项：目标机器生产镜像完整演练与HTTPS/SMTP接入、真实并发压测及容量数据、私有歌单拖拽编辑/手动添加更多入口、旧后台全量审计、长期指标留存、向量检索与推荐评测。以上没有伪装成已经完成的功能。
