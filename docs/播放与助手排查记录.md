# 播放与助手排查记录（2026-10-26）

## 截图中的现象与原因

1. **播放和封面失败**：本机Java后端仍运行，但3001端口的Node音源侧车已经退出。日志出现 `Connection refused`，播放器无法从侧车获取媒体。进程为何退出没有足够历史证据，不能直接归因于Redis或歌曲版权。
2. **Jamendo“暂不可用”**：实际接口返回HTTP200、`songs:null`，原适配层只接受数组，将正常空结果抛成异常。修复后同查询返回空数组，界面显示“无结果”。真正超时/错误则显示“检索失败”，不代表整个网站断网。
3. **“尚未验证”**：这是播放完整性记录，不是连接状态。Meting返回的部分曲目没有标称时长，即使媒体已经起播，也无法确认音频是否等于整曲。现在统一写作“完整性未知”，使用中性色和说明；播放器会单独显示“正在播放”“正在缓冲”。“时长匹配”只代表时长相符，不表示完整播放验证通过。
4. **机器人状态矛盾**：模型状态接口读取超时被直接写成无法连接，客户端仅在打开对话框时检查一次，后续聊天成功也没有更新。现在区分连接失败与探测超时，对话框打开时约每20秒检查、聊天结束后刷新，并显示检索和生成阶段。
5. **推荐偏离需求**：小模型把“悲伤音乐”等情绪词直接作为标题搜索，返回的多是标题包含这些词的上传内容。直接测试本机3B模型还观察到歌名和歌手搭配错误。现在常见低落/治愈与摇滚需求先使用人工编排的具体检索词，查询真实曲库并严格核对歌名和歌手，再把真实候选交给模型生成简短建议。这里不是新训练的推荐模型，也没有向量库。

## 实施的调整

- 音源通过本机监护进程运行，工作进程退出后记录原因并退避重启；保留所有者核验与停止脚本清理。启动入口仍为根目录 `scripts/start-dev.ps1`。
- 新增独立的上游响应解析与测试，区分空结果、坏数据和真实错误，防止空结果触发源冷却。
- 搜索结果跨平台合并后重新排序，精确歌手和歌名优先；例如“罗大佑”现在先显示其本人歌曲，而不是标题包含其姓名的其他歌手作品。
- 完整性未知使用灰色提示，缓冲状态由真实音频事件驱动。不会将未知、长音频或成功打开的链接直接标成完整版本。
- 助手预检索不使用静态歌曲卡片：人工检索词必须在源站返回结果中找到，排除同名翻唱/混音冒充指定录音；没有匹配候选时说明未找到。严格完整模式仍排除未知资源。
- 候选卡片可以在模型生成说明前发送。正常工具失败返回事实性状态，去掉“请告知用户”这样的内部指令文本。
- 防止模型空回复以正常结束帧结束，提供明确的空回复说明。客户端同步识别检索/生成阶段事件，并验证探测失败后能恢复连接状态。

`supervise.mjs` 只负责工作进程退出后的恢复；系统重启或监护进程本身被结束后，需要重新运行启动脚本。它不是对所有上游故障的自动修复。浏览器刷新会清空本次完整性证据，这是有意设计。

## 2026-11-01：播放控制与异步请求竞争修复

本轮检查时后端和 Provider 健康接口均正常。对真实在线资源使用 Range 请求抽查，多个资源返回 206 音频，个别 QQ/Meting 资源返回 404，说明不能将所有播放失败归因于服务未启动。

修复内容：

- 新增独立播放意图及请求代号。实际播放状态由原生 `playing` 事件更新，等待加载时仍能点击暂停；暂停会使旧的播放请求失效。
- 用户端歌曲列表、首页、收藏、歌单、最近播放、合集和助手统一调用 `play()`，由音频引擎负责加载，避免外部 `await loadTrack(); play()` 在用户暂停后继续启动音乐。
- 自动换源结果同样校验播放请求是否仍有效；暂停或切换歌曲后，旧查询不会再应用替代资源或自动起播。
- 用户明确重试时刷新失败资源并重置替代尝试集合；自动替代保持原尝试上限，避免无限循环换源。
- 加载新歌即重置时间、总时长与拖动状态；浏览器阻止播放时清理等待状态。
- 单曲循环仅影响自然播完，手动上一首/下一首仍移动队列。顺序模式末尾停止；合集最后一个失败条目也停止。
- 忽略过期的暂停/结束/错误事件，避免新歌被旧媒体事件干扰。

验证：25 项前端单元测试与类型检查通过，生产构建成功。浏览器回归使用真实生成的 WAV 和受控的延迟/404 响应，覆盖加载暂停、快速切歌、旧选择迟到、暂停换源、重试恢复、顺序结束，并保留歌词、导入、工作区及助手回归。真实本地服务下，《童年》浏览器起播超过 2 秒，识别时长 233.17 秒，无未捕获页面异常；没有据此声称整曲完整播放或所有音源可用。

本轮不涉及后端接口或数据库修改。用户刷新前端即可；第三方资源本身的 404、试听或权益限制仍可能发生，替代资源仍须满足既有歌手、版本、时长匹配规则。
